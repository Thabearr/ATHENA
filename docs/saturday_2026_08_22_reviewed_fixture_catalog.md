## Why the admission decision is not auto-stored

ATHENA's existing source-replayed admission contract deliberately separates `prepare-decision` from `store`.

The exact decision bytes cryptographically bind the current clean Git HEAD, candidate/review/handoff hashes, catalog hash, manifest hash, and the reviewed FotMob source-capability profile. They must be reviewed as exact bytes before storage. Therefore this preparation script never calls the admission store and records `catalog_admission_stored=false`.

The hosted workflow preserves that separation. On the PR head it produces the exact catalog, manifest, decision candidate and preparation receipt for inspection. After merge, the same workflow can replay on the exact merge commit. The first merge-commit run publishes the new exact decision candidate but refuses to store admission until a PR conversation comment explicitly approves that candidate's SHA-256. Re-running the same failed job on the same merge commit then requires the regenerated decision SHA to equal the approved SHA before invoking the existing `store` command.

This avoids silently treating a decision reviewed on the PR head as approval for a different merge-commit catalog manifest.

## Authority boundary

- new FotMob network acquisition;
- automatic fixture review;
- global team or competition identity resolution;
- Fixture Intelligence football facts;

- model-league reliability claims;
- SportyBet event or market reconciliation;
- fresh bookmaker pricing;

- selection or accumulator acceptance;

Even after a successful exact catalog admission, the 50 identities must still pass the later Fixture Intelligence, model, SportyBet, pricing, value, selection, correlation and risk gates before any requested fold can be assembled.
